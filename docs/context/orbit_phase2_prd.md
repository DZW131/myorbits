# Orbit Phase 2 PRD（产品需求文档）

版本：V0.2
状态：作为 Orbit V0.2 Phase 2 的产品基线
对应技术文档：`docs/context/orbit_phase2_technical_spec.md`
适用范围：Orbit V0.2 第二阶段——模板态分支保存、识别、拉取、应用、bindings 复用

---

## 1. 文档目的

本文档从产品视角定义 Orbit 第二阶段要解决的问题、用户价值、范围边界、核心流程、功能要求与验收标准，用于：

- 对齐产品目标与实现边界；
- 约束 CLI 行为与交互口径；
- 为技术方案、实现排期、测试用例提供上层依据。

本文档不展开底层 Git 实现细节、元数据 schema 细节与算法细节，这些内容由配套技术方案文档承接。

---

## 2. 一句话定义

**Phase 2 = 让 Orbit 拥有“运行态导出模板态、模板态作为分支沉淀、模板态跨仓库拉取、模板态再次应用为运行态”的完整闭环。**

---

## 3. 背景与问题

当前 Orbit 已经可以在仓库中以运行态方式使用，但还缺少一个关键能力：

- 不能把某个 orbit 抽象成一个可复用、可传播、可再次应用的模板分支；
- 不能稳定地区分模板态分支、运行态分支和普通分支；
- 不能从别的仓库直接拿来一个 orbit 模板并落到当前仓库；
- 不能优先复用当前仓库已有的 bindings 信息，从而减少重复填写。

你要的并不是单纯“导出几份文件”，而是一套完整的 orbit 生命周期：

1. 在运行态仓库中维护一份变量-值表；
2. 将运行态文件按该表抽象成模板态；
3. 在保存为模板 branch 前进行最后一次只作用于模板的编辑；
4. 将模板态分支保存在本地 Git 分支中；
5. 让 Orbit 能识别某个分支属于模板态、运行态还是普通分支；
6. 从本地或远程 Git 仓库拉取模板态分支；
7. 应用到当前仓库时，优先使用本地已有变量表，缺失项再由用户填写；
8. 若仓库已有同 orbit，则给出警告并让开发者决定是否覆盖。

---

## 4. 产品目标

### 4.1 主目标

建立 Orbit 的模板态产品闭环，使 Orbit 不只是“本地被使用”，还可以：

- 被抽象成模板；
- 被保存为本地模板 branch；
- 被识别和管理；
- 被从其他仓库拉取；
- 被再次应用到新仓库或新分支。

### 4.2 子目标

1. 保存模板态时只保存 orbit view 下的文件；
2. 保存模板态时支持运行态值替换为 `$var`；
3. 保存模板态前支持一次“最终模板编辑”；
4. apply 时优先复用本地 `.orbit/vars.yaml`；
5. 变量文件支持“变量说明（可选）”；
6. 远程 Git 仓库未指定 branch 时，系统可按规则自动选模板源；
7. 已有 orbit 冲突时，不静默覆盖。

---

## 5. 非目标

本阶段不处理以下内容：

1. 模板市场 / 模板注册中心；
2. 模板权限管理与团队审批流；
3. 复杂变量类型系统（首版以字符串为主）；
4. 运行态与模板态的双向自动同步；
5. 多人同时编辑模板 branch 的高级合并协议；
6. 与托管平台 API 的深度集成（V0.2 只依赖标准 Git 能力）；
7. 对运行态内容进行高度智能化的变量自动抽取与推荐。
8. `AGENTS.md` 的完整共享文件追加合并能力（V0.2 主线只保留扩展位；若在本轮收尾阶段实现，按独立方案单列推进）。

## 6. 目标用户

### 6.1 Orbit 作者

典型诉求：

- 我已经在一个项目中整理好了 orbit，希望把它沉淀成可复用模板；
- 我希望保存前先把某些固定值替换成变量；
- 我希望做一次模板专属修订，但不影响当前运行中的仓库内容；
- 我希望以后在其他项目里直接复用这个 orbit。

### 6.2 Orbit 使用者

典型诉求：

- 我想从本地或别的远程 Git 仓库拿一个 orbit 模板过来用；
- 我不想每次都从头填写全部变量；
- 如果我仓库里已经有类似 orbit，我希望系统先提醒我；
- 我希望没有变量的模板能直接应用成功。

## 7. 核心概念

### 7.1 Orbit

一个逻辑视图单元，定义“哪些文件属于它”。

### 7.2 Orbit View

某个 orbit 对应的一组路径范围。保存模板态时，只处理该范围内文件。

### 7.3 运行态（Runtime State）

当前仓库工作区中实际使用的具体内容，文件里是具体字符串。

### 7.4 模板态（Template State）

可复用、可再应用的抽象内容，文件里允许出现 `$var_name` 占位符。

### 7.5 运行态变量-值表

位于 `.orbit/vars.yaml` 的仓库级 bindings 文件，用于：

- 指定哪些值应被视为变量；
- 提供变量当前值；
- 为变量提供可选说明；
- 在模板保存和模板应用时复用。

示例：

```yaml
schema_version: 1
variables:
  project_name:
    value: Orbit
    description: 项目名称，用于文档标题、说明文字等
  owner_name:
    value: Yixin
    description: 负责人姓名，可选
  service_url:
    value: http://localhost:3000
    description: 服务访问地址
```

说明：

- `value`：变量当前值；
- `description`：变量说明，可选，用于帮助开发者理解变量含义与填写方式。

### 7.6 模板态分支（Template Branch）

一个本地或远程 Git branch，用来保存某个 orbit 的模板态快照及其模板元信息。

### 7.7 运行态分支（Runtime Branch）

一个包含合法 Orbit 配置与 orbit definitions、可作为运行态仓库使用的工作分支。

### 7.8 普通分支（Plain Branch）

未启用 orbit，也不带可识别 orbit 元信息的普通 Git 分支。

---

## 8. 产品范围

本阶段包含 5 个能力域：

1. **模板态保存**：将某个 orbit 保存为本地模板 branch；
2. **模板态最终编辑**：保存前进行一次只作用于模板态的编辑；
3. **分支类型识别**：识别 template / runtime / plain；
4. **模板态应用**：从本地或远程模板源把 orbit 应用到当前仓库；
5. **bindings 复用与补填**：优先使用本地变量表，缺失项再让用户填。

---

## 9. 功能需求

## 9.1 模板态保存

### 9.1.1 保存入口

系统应允许用户指定某个 orbit，并将其保存到一个本地模板态分支。

### 9.1.2 保存范围

保存时只应包含：

- 该 orbit view 下的文件；
- 模板态 branch 所需元信息；
- 模板变量定义信息。

保存时不应包含：

- orbit view 外的文件；
- 与该 orbit 无关的本地改动；
- 运行态 `.orbit/` 的无关状态文件。

### 9.1.3 变量替换

保存模板态前，系统应读取运行态仓库 `.orbit/vars.yaml`，将 orbit view 文件中命中的值替换为变量占位符。

例如：

- `Orbit` -> `$project_name`
- `http://localhost:3000` -> `$service_url`

### 9.1.4 变量说明支持

变量文件中的 `description` 为可选字段。系统在以下环节应尽量展示它：

- 保存前变量确认；
- apply 时交互式填写；
- 生成 YAML skeleton；
- 编辑器填写界面。

### 9.1.5 保存前确认

系统应允许开发者在真正写入模板 branch 前确认：

- 哪些值被替换成了哪些变量；
- 是否存在歧义替换；
- 最终模板包含哪些变量；
- 是否继续保存。

### 9.1.6 无变量模板

若某个 orbit 不含变量，也应允许保存为模板 branch，并成功落盘。

---

## 9.2 模板态最终编辑

### 9.2.1 功能定义

保存模板态分支时，系统应支持一个“最终模板编辑”阶段。

### 9.2.2 触发时机

在：

1. 已读取 orbit view 文件；
2. 已完成变量替换；
3. 但尚未写入模板 branch 之前。

### 9.2.3 语义要求

该编辑只影响即将保存的模板态结果，不应回写当前运行态工作区。

### 9.2.4 适用场景

- 删除仅适用于当前项目的说明；
- 增加模板使用说明；
- 调整模板标题、结构、注释；
- 对模板做通用化修饰。

### 9.2.5 保存前再校验

若开发者在最终模板编辑阶段新增或删除变量占位符，系统在写入模板 branch 前应再次扫描模板变量集合，确保模板元信息与实际模板一致。

---

## 9.3 分支类型识别

### 9.3.1 识别类型

系统至少应识别三类分支：

- `template`
- `runtime`
- `plain`

### 9.3.2 识别能力

系统至少应支持：

- 查看当前分支类型；
- 列出仓库中所有 orbit 相关分支；
- 查看某个分支关联的 orbit 信息。

### 9.3.3 展示信息

至少应包含：

- branch 名称；
- branch 类型；
- orbit 标识；
- 是否为默认模板分支；
- 来源信息（可选）；
- 对于模板 branch，是否存在变量定义。

---

## 9.4 模板态应用

### 9.4.1 应用来源

系统应支持以下来源：

- 当前仓库中的本地模板态分支；
- 其他远程 Git 仓库中的模板态分支；
- 其他远程 Git 仓库（未显式指定分支，由系统自动解析）。

### 9.4.2 应用结果

应用成功后，模板态文件经 bindings 渲染为运行态内容，并写入当前工作区。

### 9.4.3 应用后状态

应用成功后，当前仓库/当前分支应写入：

- 对应的 orbit definition；
- 该 orbit 的模板来源记录；
- 必要时更新后的本地变量表。

应用模板不应自动切换当前工作区 projection；如需进入该 orbit，由用户显式执行 `orbit enter <orbit-id>`。

### 9.4.4 无变量模板

无变量模板应可直接应用成功，不要求用户填写 bindings。

---

## 9.5 apply 时 bindings 复用

### 9.5.1 自动复用本地变量表

当 apply 一个模板态 orbit 时，系统应优先读取当前仓库 `.orbit/vars.yaml`，自动复用同名变量的值。

### 9.5.2 缺失项补填

只有模板需要、但本地变量表中没有的变量，才要求用户填写。

### 9.5.3 复用时展示说明

若变量存在 `description`，在补填界面中应一并展示，以减少歧义。

`description` 的展示优先级应稳定：

1. 优先使用 template manifest 中该变量声明的 `description`；
2. 若 manifest 未提供，再按值来源优先级回退：
   `--bindings` 文件 > 当前仓库 `.orbit/vars.yaml` > 交互式 / editor 补填结果。

该规则只影响说明文字展示，不改变变量值本身的合并优先级。

### 9.5.4 结果要求

同一个模板 + 同一份变量值，应能稳定生成一致的运行态结果。

---

## 9.6 bindings 提供方式

系统应支持至少 4 种方式：

### 9.6.1 交互式逐项输入

CLI 逐项询问变量值。

### 9.6.2 YAML 文件填写

系统可生成只包含变量键的 YAML skeleton，开发者填写后再 apply。

### 9.6.3 编辑器式填写

系统可打开本地文档进行填写，再回到 CLI 继续流程。

### 9.6.4 直接指定 bindings 文件

用户可在 apply 命令中直接传入一个现成 YAML 文件。

---

## 9.7 已有 orbit 冲突处理

### 9.7.1 冲突定义

当当前仓库中已存在某个 orbit 时，再拉取/应用同一 orbit，应视为冲突。

至少包括：

- 相同 orbit id；
- `.orbit/orbits/<orbit-id>.yaml` 已存在且内容不同；
- `.orbit/installs/<orbit-id>.yaml` 已存在且来源不同；
- 模板将写入的目标路径已存在内容冲突或未提交改动。

### 9.7.2 默认行为

系统不应静默覆盖，而应给出警告，并让开发者选择：

- 覆盖已有 orbit；
- 放弃当前操作；
- 预览后决定（增强项）；
- 改名导入（增强项）。

---

## 9.8 远程 Git 仓库模板分支解析

### 9.8.1 适用场景

当用户只提供远程 Git 仓库 URL，而没有指定模板 branch 时，系统应自动定位可用的 orbit 模板分支。

V0.2 默认以 GitHub URL 场景进行验收，但解析机制本身只依赖 Git 引用与模板 manifest，不依赖平台 API。

### 9.8.2 解析规则

按以下优先级处理：

1. **唯一模板分支优先**：若仓库中只有一个合法 orbit 模板态分支，则直接使用；
2. **唯一默认模板分支兜底**：若存在且仅存在一个被标记为默认模板分支的模板 branch，则自动使用，并给出低打扰提示；
3. **多模板分支人工选择**：若存在多个模板分支且无默认模板分支，则列出候选项，要求开发者手动选择。

### 9.8.3 异常场景

若远程仓库不存在任何合法 orbit 模板分支，则应明确报错。

## 10. 关键用户流程

## 10.1 保存模板态分支流程

1. 用户指定某个 orbit；
2. 系统读取 orbit view 范围内文件；
3. 系统读取 `.orbit/vars.yaml`；
4. 系统按变量-值表执行值替换；
5. 系统展示变量替换结果与可选说明；
6. 用户确认是否继续；
7. 若指定最终模板编辑，则打开模板态结果进行编辑；
8. 系统再次扫描模板变量；
9. 系统创建或更新模板态 branch；
10. 写入模板态文件与模板元信息；
11. 保存完成。

## 10.2 从本地模板 branch 应用流程

1. 用户指定本地模板分支；
2. 系统校验该 branch 为合法模板态分支；
3. 系统检查当前仓库中是否已有同 orbit；
4. 若已存在，则警告并等待用户决策；
5. 系统读取模板变量列表；
6. 系统读取当前仓库 `.orbit/vars.yaml`；
7. 同名变量自动填充；
8. 缺失变量再让用户填写；
9. 系统渲染运行态文件；
10. 写入当前工作区；
11. 更新 `.orbit/orbits/<orbit-id>.yaml`、`.orbit/installs/<orbit-id>.yaml`，必要时更新 `.orbit/vars.yaml`；
12. 应用完成。

## 10.3 从远程 Git 仓库应用流程

1. 用户指定远程 Git 仓库 URL；
2. 若未指定 branch，系统自动解析模板分支；
3. 后续流程同本地模板应用；
4. 成功后记录远程来源信息。

## 11. CLI 需求口径

本阶段 CLI 以以下口径为准：

### 11.1 模板保存

```bash
orbit template save <orbit-id> --to <template-branch>
```

可选参数：

- `--overwrite`
- `--edit-template`
- `--default`
- `--dry-run`

### 11.2 本地模板应用

```bash
orbit template apply <template-branch>
```

可选参数：

- `--bindings <file>`
- `--interactive`
- `--editor`
- `--overwrite-existing`
- `--dry-run`

### 11.3 远程模板应用

```bash
orbit template apply <git-url>
```

可选参数：

- `--ref <template-branch>`
- `--bindings <file>`
- `--overwrite-existing`

### 11.4 生成 bindings skeleton

```bash
orbit bindings init <template-source> --out ./orbit-bindings.yaml
```

### 11.5 分支状态查看

```bash
orbit branch status
orbit branch list
orbit branch inspect <branch-name>
```

## 12. 成功标准

本阶段完成后，应满足以下产品结果：

1. 开发者可以把某个 orbit 可靠地保存为模板态分支；
2. 保存时能按运行态变量表把值替换成变量；
3. 保存前能进行一次只作用于模板的编辑；
4. Orbit 能识别模板 branch、运行态 branch 和普通 branch；
5. 开发者可以从本地模板或远程 Git 仓库应用 orbit；
6. apply 时优先复用本地变量表，减少重复输入；
7. 变量文件支持可选说明，并能在交互中被利用；
8. 已有 orbit 冲突时系统会提醒，而不是静默覆盖。

---

## 13. 验收标准

### 13.1 模板保存

- 能将某个 orbit 成功保存到本地模板 branch；
- 模板 branch 只包含 orbit view 下文件；
- 模板文件中出现变量占位符；
- 保存前可确认变量替换结果；
- 变量说明可被读取并展示；
- 无变量模板也可保存成功。

### 13.2 模板最终编辑

- 可在模板落盘前打开模板态结果进行编辑；
- 编辑结果只进入模板 branch；
- 当前运行态工作区不被改动；
- 编辑后若变量集合变化，系统会重新校验。

### 13.3 分支识别

- 能识别当前 branch 为 `template` / `runtime` / `plain`；
- 能列出所有 orbit 相关分支；
- 能查看模板分支的 orbit 基本信息。

### 13.4 模板应用

- 能从本地模板分支应用 orbit；
- 能从远程 Git 仓库应用 orbit；
- apply 成功后当前仓库写入运行态文件；
- apply 成功后当前仓库写入 orbit definition 与模板来源记录；
- apply 成功后不会自动 `enter` 该 orbit。

### 13.5 bindings 复用

- apply 时可自动复用本地 `.orbit/vars.yaml`；
- 只有缺失变量才提示用户填写；
- 变量说明在提示界面中可见；
- 直接指定 bindings 文件可成功 apply。

### 13.6 冲突处理

- 当前仓库已有同 orbit 时会提示；
- 默认不会静默覆盖；
- 用户可显式选择覆盖或取消。

### 13.7 远程模板解析

- 唯一模板分支场景可自动命中；
- 恰好一个默认模板分支场景可自动命中；
- 多模板且无默认模板时可列出候选并让用户选择；
- 无模板分支时会明确报错。

---

## 14. 版本拆分建议

### 14.1 Phase 2A：模板保存闭环

先交付：

- `.orbit/vars.yaml` 读取；
- 模板保存；
- 保存前变量确认；
- 最终模板编辑；
- 模板 branch 元信息。

### 14.2 Phase 2B：本地模板应用闭环

再交付：

- 本地模板 apply；
- 本地变量表复用；
- 缺失变量交互填写；
- 冲突提示；
- 安装来源记录。

### 14.3 Phase 2C：远程模板源

最后交付：

- 远程 Git 仓库模板分支解析；
- 远程模板拉取与应用；
- 远程来源记录；
- bindings skeleton / 编辑器填写增强。

## 15. 风险与注意事项

1. **变量替换歧义**：同一值可能对应多个变量，必须有确认机制；
2. **模板编辑后二次失配**：最终模板编辑可能引入新变量，必须重新校验；
3. **已存在 orbit 覆盖风险**：默认必须警告；
4. **远程模板解析歧义**：多模板分支场景下必须转人工选择；
5. **本地变量复用误用风险**：同名变量可能语义不一致，必要时应允许复核。

## 16. 最小可交付版本定义

真正可以开始写代码的最小版本应具备：

- `.orbit/vars.yaml` 支持 `value` + `description`（可选）；
- `orbit template save`；
- 运行态值替换为模板变量；
- `--edit-template`；
- 模板 branch 元信息；
- `orbit template apply <template-branch>`；
- apply 时复用 `.orbit/vars.yaml`；
- 缺失变量交互填写；
- 当前仓库 orbit 冲突提示。

在此基础上，再补远程 Git 仓库支持。

## 附：AGENTS.md 功能定位

由于 `AGENTS.md` 在多个 orbit 中往往会重复出现，且处理策略通常为“内容追加”而不是“整文件覆盖”，它不宜被当作普通 orbit 文件处理。

因此，Phase 2 PRD 中仅要求主线产品为此预留扩展能力与冲突口径；完整的 `AGENTS.md` 共享文件方案、开发阶段与交互细节，见单独文档：`docs/context/orbit_agents_md_development.md`。
